## What upstream brought

One commit: `c3b2f73`, [carderne/pi-sandbox#88](https://github.com/carderne/pi-sandbox/pull/88), "sandboxed bash respects shellCommandPrefix".

- **Change.** `src/extension.ts` reads pi's `settings.getShellCommandPrefix()` next to `getShellPath()` and passes it as `commandPrefix` to both bash tool definitions: the unsandboxed `localBash` fallback and the sandboxed `createBashToolDefinition(... createSandboxedBashOps(...))`. pi's bash prepends the prefix as `${prefix}\n${command}` before `operations.exec`, so on the sandboxed path it runs **inside** the sandbox wrapper. `test/session-isolation.test.ts` gains the darwin-only test "sandboxed bash respects shellCommandPrefix".
- **Why it matters.** pi's built-in bash honours `shellCommandPrefix`. Before #88, loading this extension in default mode silently dropped the setting (alias/env sourcing, `shopt`, …). Now the prefix behaves the same whether or not the sandbox is loaded. Advancing the freeze point also keeps the next sync a one-hop merge.
- **Nothing else moved.** No new release, no `package.json` change upstream, and no `@carderne/sandbox-runtime` bump (the D2 pin stays). `getShellCommandPrefix` exists across our `^0.80.0` pi range, so pi needs no dependency bump.
- **Who sees a change today.** Only profiles in default mode with a prefix set. The personal profile runs hook mode (D10) and sets no prefix, so it sees none. The work profile is unverified (see Pending).
